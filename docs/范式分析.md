# 范式分析

> 对象：`832_research_sample.sqlite` 的 22 张表（18 张实体表 + 4 张联系表）
> 目的：说明每张表达到了第几范式、哪些地方是**有意反规范化**、哪些是**真正需要改**的。
> 文中所有数字都可以用第七节的 SQL 复现。

---

## 一、结论速览

| 判定 | 表 | 说明 |
|---|---|---|
| 3NF 且 BCNF（16 张） | 其余 16 张实体表与联系表 | 决定因素全是候选键，无传递依赖 |
| 3NF，但存在**受控冗余**（2 张） | `deliverable_version`、`project_snapshot` | 冗余是为留痕或对账，需在设计说明中声明 |
| 3NF，但**人物未抽成实体**（1 张） | `person_mention` | 已补 `UNIQUE(报道ID, 人物名)` 防重，实体化留作扩展 |
| **1NF 未达标**（2 张） | `evidence_issue`（JSON 数组）、`project_location`（1 行含 9 个村名） | 前者有意，后者为原文保真 |
| 需要讨论（1 张） | `government_project` | 若 `project_name → category` 成立则违反 3NF/BCNF |

`public_report.title` 原先与 `source_document.title` **297/297 完全相同**，已在 2026-11-17 删除该列，标题统一取自 `source_document`（详见 4.1）。

一句话：22 张表里 **16 张严格 3NF/BCNF**；**5 处**需要在报告里解释（2 处受控冗余、1 处实体未抽、2 处 1NF 让步），另有 1 处待验证依赖。**原本唯一“该改没改”的 `public_report.title` 已按 3NF 修正。**

## 二、判定方法

范式判定不是背定义，是三步：

1. **找候选键**：能唯一确定一行的最小属性组。代理键（`report_id` 这类流水号）本身总是候选键，但不代表它是唯一候选键。
2. **写函数依赖**：`X → Y` 表示 X 定了，Y 就定了。只写由业务规则保证的依赖，不写“数据碰巧如此”的依赖。
3. **逐级检查**：
   - **1NF**：每个属性不可再分（不能是一组值）；
   - **2NF**：在 1NF 基础上，非主属性不存在对候选键**真子集**的部分依赖（只有复合键才可能违反）；
   - **3NF**：在 2NF 基础上，非主属性之间不存在传递依赖（`X→Y→Z`）；
   - **BCNF**：所有非平凡函数依赖的决定因素都是候选键。

**代理键的影响**：本库绝大多数表用流水号做主键（`report_id`、`version_id`…）。这会让 2NF 自动成立（单属性键没有真子集），但**不能免除 3NF 检查**——因为 3NF 检查的是非主属性之间的关系，与主键形态无关。下面逐表检查的正是这一点。

## 四、八处需要展开说明的地方

### 4.1 `public_report.title`：已删除（2026-11-17 修正）

**原问题**：297 条报道的 `title` 与它对应 `source_document.title` **297 条全部相同**（`diff = 0`）。同一事实存两张表，改一处就会不一致——典型更新异常。

**处理**：删列。`public_report` 现在只保留 `report_id / document_id / county_id / published_date`，标题一律通过 `JOIN source_document` 取得。同步改动 4 处：

| 位置 | 改动 |
|---|---|
| `832_schema.sql` | `public_report` 去掉 `title` 列 |
| `build_sample_db.py` | `INSERT` 去掉 `title` |
| `app.py` `reports()` | 检索与展示改取 `d.title` |
| `render_db_demo.py` | 两处 `r.title` 改为 `d.title` |

**验证**：重建后 297 篇报道、313 份文档、6 条查询结果与改动前完全一致；`test_backend.py` 29/29 通过。

**代价**：报道检索多一次 JOIN（本来就已经 JOIN 了 `source_document` 取 URL，所以**实际没有增加任何连接**）。

### 4.2 `deliverable_version.kind`：有意保留的历史快照

`kind` 的值与 `field_task.required_kind` **4 条全部一致**。看起来可以删，但**不能删**：

> 假如队长把任务 T-003 的应交材料从“案例报告”改成“资料包”，历史第 1 版仍是按“案例报告”交的。如果版本表不自己存一份 `kind`，历史就会被改写——审核记录会指向一个“从来没交过的材料类型”。

这不是冗余，是**时间维度上的取值快照**。相同的道理让 `audit_log` 存动作文本而不是只存枚举码。

### 4.3 `project_snapshot.budget_wan` 与 `project_location` 的合计：校验冗余

**事实**：43 个项目的 `budget_wan` 与其实施地点行金额之和**全部相等**（核对查询返回 0 行）。

**为什么两处都存**：
- 只存 `budget_wan`：无法验证明细，158 行金额错了也看不出来；
- 只存行合计：一旦某项目没有实施地点行，预算就丢了。

两处都存，才能做**勾稽**——这正是本系统区别于普通档案系统的地方。它不是“派生列写错了”，而是**故意保留的两份独立记录，让不一致暴露出来**。

> 若老师问“这违反 3NF 吗”：不违反。`budget_wan` 依赖 `(项目, 口径, 版本标签)`，不依赖任何非主属性；两份数据之间是“业务校验关系”，不是函数依赖。

**这里还有一个 4NF 层面的细节值得说**：一个项目同时有“多个金额版本”和“多份依据文件”。如果合成一张表、且两者互相独立，就会出现多值依赖（`项目 →→ 版本`、`项目 →→ 文件`），必须拆表。本库用 `UNIQUE(project_id, snapshot_kind, version_label)` 强制版本与文件一一对应，从而避免了 4NF 问题——这是有意为之的约束设计。

### 4.4 没有抽字典表的三处：不是范式问题，是归一化问题

`industry_case.industry`（6 个取值全不相同：木耳、禽业、莲藕、制造业、乡村旅游、农产品流通）、`user_account.role`、各表的状态字段，都是**字符串枚举而非外键**。

- **范式上无问题**：`industry` 依赖 `case_id`，没有非主属性之间的依赖；
- **但存在归一化风险**：报道原文可能写“黑木耳”，另一个人录成“木耳”，按产业聚合就会裂成两类。

**取舍理由**：这三处保留原文表述，是为了不篡改来源说法（证据系统最忌“统一口径”）。代价是无法稳定按产业维度统计——这要在报告里如实说明，并作为“后续可加 `industry` 字典表 + 映射表”的扩展点。

### 4.5 `person_mention`：形式 3NF，但“人物”没被当作实体

**更正**：我此前说“`person_mention` 不算严格 3NF”，**这个说法是错的**。它只有一个主键 `mention_id`，`role_text`、`context_summary` 依赖整行，没有传递依赖，**它是 3NF 的**。

真正的问题是**建模粒度**，不是范式：
- 目前 4 条记录全部来自同一篇报道（`report_id = 231`），所以暂时没有重复；
- 一旦人物跨报道出现，`person_name` 字符串就会重复存储，且“此人是谁”无法作为实体被引用；
- 想按人物做跨县聚合（示例 2 的“查找同一政策涉及的不同受访者”），只能 `GROUP BY person_name` 字符串，拼写差一个字就分裂。

**改法（若要做人物维度分析）**：抽 `person(person_id, name)`，`mention(report_id, person_id, role_text, context_summary)`，把 `role_text` 留在联系上——因为同一个人在不同报道里身份不同，这正是“联系带属性”的又一例。

**另外这里原先缺一条约束，已补**：`person_mention` 之前只有 `mention_id` 主键，没有 `UNIQUE(report_id, person_name)`，同一篇报道里的同一个人可以被录入两次而数据库不报错。2026-11-17 已添加：

```sql
CREATE UNIQUE INDEX idx_mention_unique ON person_mention(report_id, person_name);
```

实测：现有 4 条记录（全部来自 `report_id = 231`，姓名互不相同）无冲突，索引创建成功，重复插入会被拒绝。

### 4.6 `government_project`：一个待验证的潜在违规

`project_name` 不是候选键（跨县、跨年可重名），但在当前 43 条数据里：**重名项目 0 个，同名不同类别 0 个**。

如果业务规则是“项目名称决定项目类别”（即 `project_name → category`），那么 `category` 传递依赖于非主属性，**违反 3NF 和 BCNF**。

**结论要谨慎**：43 条样本不足以证明这条依赖，且现实中不同县完全可能用同名项目归入不同类别。报告里应当写成“**在当前样本中未见反例，但该依赖不被业务规则保证，故不视为函数依赖**”——这样回答既严谨又显专业。

### 4.7 `project_location` 的 1NF 例外：一处原文保真

158 条里 **1 条**的实施地点是 9 个村名用“、”连在一行：

> 南秋兰村、杨家庄村、北封村、冀家沟村、樊家台村、台头村、西明义村、丁家洼村、西官庄村

严格说这是多值属性，违反 1NF。**但不建议拆**：这一列命名为 `_raw`，就是声明“这是原表单元格的原文”，拆开等于替政府表格重写内容，一旦拆错就不可复原。

正确做法是**保留原文 + 另设规范行**（如果需要按村统计，再建 `project_village(project_id, village_name, amount)`）。这也解释了为什么表里同时有 `xlsx_row`：目的是任何一行都能回到原表的第几行去核对。

### 4.8 `evidence_issue.facts_json`：真正违反 1NF 的一处

```json
["项目库编号6预算60万元，预计受益数字栏为114人，但同一行绩效目标文字称97户383人…",
 "年初绩效目标编号78和年中目标编号67均称30户114人、户均增收2000元。",
 "进度表编号61预算60万元，状态为完工。"]
```

一个字段存了整个数组——典型的多值属性。

**两种改法**：
- 方案 A（推荐，严格 1NF）：`evidence_issue_fact(issue_id, seq, fact_text)`，一条事实一行，还能给单条事实挂来源文档；
- 方案 B（务实）：保留 JSON，在报告中声明“这是结构化备注，不参与任何检索与统计，只作人工核对时的说明”。

**现状选 B**（8 条记录，纯人工阅读用，不参与查询）。但**必须在报告里承认这是 1NF 例外**，否则老师一翻表就能看出来。

## 六、被追问时的三个标准答案

**Q：为什么用代理键而不是自然键？**
`report_id`、`version_id` 这类流水号与业务无关，好处是主键稳定（县政府可能改项目编号、报道可能改标题），坏处是丢失业务约束。所以本库的做法是**代理键做主键 + 自然键加 UNIQUE**：`source_document.url` 唯一、`deliverable_version(task_id, version_no)` 唯一、`task_assignment(task_id, user_id)` 复合主键。这样既稳定又不放弃约束。

**Q：这些表都是 3NF，是不是过度规范化了？**
不是。真正会带来性能问题的是“每次查询要 JOIN 七八张表”，而本库最复杂的查询（金额勾稽）也只 JOIN 三张表，且行数在千级以内。**规范化的收益（不会出现同一事实两个值）远大于这里可以忽略的连接代价。** 唯一为性能做的妥协是 3 个视图和 9 个索引（`idx_one_task_lead`、`idx_mention_unique` 两个是部分/唯一索引，同时承担约束职责）。

**Q：`project_snapshot` 和 `project_location` 为什么不能合成一张表？**
项目与金额版本是 1:n，项目与实施地点也是 1:n。合成一张表会产生**笛卡尔积膨胀**：3 个版本 × 5 个地点 = 15 行，预算被重复 5 次、地点被重复 3 次——这是典型的“多值依赖导致的冗余”，比违反 3NF 更严重。

## 七、复核用的 SQL

```sql
-- 1) 确认 public_report 已无冗余 title 列（应只剩 4 列）
PRAGMA table_info(public_report);
-- 结果：report_id / document_id / county_id / published_date

-- 2) 实施地点是否含多值
SELECT COUNT(*) FROM project_location
WHERE implementation_location_raw LIKE '%、%' OR implementation_location_raw LIKE '%；%';
-- 结果：1

-- 3) 项目是否重名、同名是否跨类别
SELECT COUNT(*) FROM (SELECT project_name FROM government_project
GROUP BY project_name HAVING COUNT(*) > 1);
SELECT COUNT(*) FROM (SELECT project_name FROM government_project
GROUP BY project_name HAVING COUNT(DISTINCT category) > 1);
-- 结果：0 / 0（样本 43 条，不足以证明依赖）

-- 4) 版本的 kind 是否与任务应交材料一致
SELECT v.version_id, v.kind, t.required_kind
FROM deliverable_version v JOIN field_task t ON t.task_id = v.task_id;
-- 结果：4 条全部一致（属有意快照）

-- 5) 人物是否跨报道重复
SELECT person_name, COUNT(*) n FROM person_mention GROUP BY person_name ORDER BY n DESC;
SELECT COUNT(DISTINCT report_id) FROM person_mention;
-- 结果：4 条人物全部来自同一篇报道（report_id = 231）
```
